# Lyric Typing Game — Project Context

A rebuild of an earlier project. Read this fully before proposing architecture; several
decisions below were made deliberately after evaluating alternatives, and the rationale is
included so they don't get re-litigated.

## What it is

A browser typing game. A YouTube music video plays; synced lyrics scroll in time with the
song; the player types each line as it's sung. Scoring is based on accuracy and how well
typing keeps pace with the vocal.

The point of the project (beyond being fun) is the **timing layer** — reconciling
lyric timestamps with an arbitrary YouTube video that we cannot analyze directly. That is
where the engineering interest lives, and it should not be treated as incidental plumbing.

## Stack

- Frontend: React (existing familiarity: Chakra UI, Zustand, React Router)
- Backend: Node + Express — required, not optional (see YouTube quota and offset store)
- Persistence: Firestore
- ~~No user accounts in v1~~ — **superseded, see "Accounts" below**

## External services and their hard constraints

### YouTube Data API v3 — search and metadata
- Free quota is 10,000 units/day. `search.list` costs **100 units per call**; `videos.list`
  costs 1. That's ~100 searches/day before throttling.
- **Therefore:** all search results must be cached server-side keyed by normalized
  artist+title. Resolve a video ID once, store it, never search for that track again.
  Client never calls YouTube directly — the API key stays server-side.
- **Built.** `server/src/youtube/` — cache, budget, ranking. Three things the constraint above
  implies that are worth stating outright, since each was a decision:
  - The **budget counter persists** (Firestore, Pacific day boundary). An in-memory counter resets
    on every dev-server restart while Google's does not, which is a way to spend a day's real quota
    without the counter ever leaving single digits.
  - The **video screen loads cache-only** and asks before spending. Opening it is not the same act
    as requesting a search, and a user who picked the wrong track should not have cost anything.
  - The **budget is checked after the cache lookup**, so exhausting it degrades the feature to
    "tracks someone has already looked up" instead of taking it out entirely.

### YouTube IFrame Player API — playback
- Playback only. The player runs in a **cross-origin iframe**, so there is:
  - no access to audio samples (no Web Audio, no AnalyserNode, no FFT)
  - no way to auto-detect timing offset by correlating audio
- `getCurrentTime()` updates coarsely (~250ms granularity). Do not drive the lyric
  highlight loop directly off it — see "Timing loop" below.

### YouTube captions — DO NOT USE
Already evaluated and ruled out. `captions.list`/`captions.download` require OAuth as the
video *owner*, so third-party captions are inaccessible via the public API. The undocumented
`timedtext` endpoint that community libraries wrap is outside the ToS and breaks
periodically — do not introduce it. Separately, auto-generated captions on sung vocals are
low quality and most music videos lack manual caption tracks anyway.

### LRCLIB — synced lyrics
- Free, no API key, no auth. Community-contributed LRC files.
- Query by artist + track + album + duration for exact match; fall back to fuzzy search.
- Coverage is good but not universal. **Missing lyrics is a normal state**, not an error —
  the app must degrade to a "no lyrics available for this track" screen, not break.
- Most entries are **line-synced, not word-synced**. Scoring must therefore tolerate the
  player finishing a line early or late within its window.

## Legal posture — important

Lyrics are publisher-copyrighted. LRCLIB is free to query but does not confer a license.

- **Do not** commit lyrics, LRC files, or a lyrics cache to the repository.
- **Do not** build a server-side lyrics cache or mirror. Fetch from LRCLIB at request time.
- Licensed alternatives (Musixmatch, LyricFind) require paid commercial agreements; the free
  Musixmatch tier returns partial lyrics only and does not include synced lyrics.
- Scraper libraries that pull lyrics via Spotify's internal endpoints are ToS violations —
  do not use or reference them.
- This ships as a personal/local project and demo. Not a public product.

The repo should be about *our code* — timing, matching, consensus, scoring. Not about content.

## Video selection — priority order

Search direction matters: **start from the canonical track** (artist, title, album, duration
from LRCLIB), then find a video for it. Never find a video first and go hunting for lyrics.

Rank YouTube candidates in this order:

1. **`Artist - Topic` channels.** Auto-generated by YouTube from the distributor's delivery —
   the exact studio master, no intro, no edit. LRC timestamps typically land with near-zero
   offset. Detect via `channelTitle` ending in `- Topic`. **This is the highest-value target.**
2. **Official Artist Channel audio/full-album uploads** — usually the same master.
3. **Lyric videos** — normally correct audio, but often a few seconds of title card first.
4. **Official music video** — *last resort*, not first choice. Frequently has spoken intros,
   label idents, edited arrangements, or a different mix.

Duration heuristic:
- Prefer `videoDuration >= trackDuration`; extra length usually means intro/outro, not a
  different recording.
- Score by excess duration, prefer the smallest positive delta.
- **Reject** videos shorter than the LRC track duration — that indicates a radio edit or a
  different version.
- Do not use a symmetric ±3s window; it's too strict on one side and too loose on the other.

**Built** — `server/src/youtube/rank.ts`, pure and fixture-tested. Two refinements the list above
did not anticipate, both discovered by writing the cases down:

- The official music video needed its own tier *below* lyric videos. Folding it into `other` would
  have ranked it alongside covers and reaction uploads, which is too harsh — it is the wrong first
  choice, not junk.
- The shortfall rejection needs about two seconds of slack. LRCLIB durations are user-supplied and
  YouTube reports whole seconds, so a one-second disagreement is the two sources rounding rather
  than a radio edit, and edits differ by tens of seconds anyway.

Rejected candidates are returned and sorted last rather than dropped, and shown behind one click
with the reason. Every rejection is a heuristic reading a title string; the user can see the video
and we cannot.

## Per-video offset store

The core system. Matching alone is insufficient — a correctly matched video can still be
shifted by a constant amount (title cards, silence, different masters). The offset reconciles
lyric timestamps to a specific video.

```
key:   `${videoId}:${lrclibTrackId}`
value: {
  submissions: [{ offsetMs, submittedAt }],
  consensusOffsetMs: number | null,
  variance: number,
  submissionCount: number
}
```

Applied at playback as `displayTime = lrcTimestamp + consensusOffsetMs`.

### How offsets are captured

The offset cannot be computed (no audio access), so a human supplies it:

- **Tap calibration:** play from start, user presses a key when the first sung line begins.
  `offset = observedTime - firstLrcTimestamp`.
- **Live nudge:** arrow keys shift lyrics ±100ms during playback. Users do this instinctively
  when it feels wrong; capture the final value as a submission.

### Consensus (do not skip this — it's the interesting part)

Individual submissions are noisy: mistaps, users calibrating against the wrong section,
occasional garbage.

- Use the **median**, not the mean — one wild outlier must not move the result.
- Weight by how many submissions cluster near that value.
- Only serve an offset above a confidence threshold. Below it, prompt the next user to
  calibrate rather than showing them a wrong offset.
- **High variance across submissions is a wrong-video signal**, not a timing problem — it
  means different arrangement/live version/extended cut. Demote that video from the match
  candidates and promote the next one. This is the automatic feedback loop that improves
  matching over time.

Once one user calibrates a video, every subsequent user gets it right on first play. Coverage
compounds.

## Timing loop

`getCurrentTime()` on the iframe player is too coarse (~250ms) to drive lyric highlighting
directly — naive polling produces visible stutter.

- Poll `getCurrentTime()` on an interval, but **interpolate against `performance.now()`**
  between polls to produce a smooth virtual clock.
- Detect and correct drift when the polled value diverges from the interpolated value beyond
  a threshold.
- Hard resync on `onStateChange` for seek, buffer, and pause events.
- Consider a user latency calibration step — audio output lag varies by device and headphones.

## Gameplay

- Lines are presented as they enter their sync window; player types the line.
- Because lyrics are line-synced rather than word-synced, scoring tolerates finishing early
  or late within the window — decide the tolerance deliberately and document it.
- **WPM is measured per line, not across the run.** Each line's clock runs from its first keystroke
  to the moment it is completed, and the run's denominator is the sum of those intervals. A song is
  mostly not typing; dividing by the run's wall-clock span would measure the arrangement's dead air
  — instrumental breaks, gaps between lines, the outro — rather than the player. Starting on the
  first keystroke rather than when the line appears follows the same logic: a line-synced window
  often opens seconds before the vocal, and that lead-in belongs to the LRC file, not the player.
- Track per-keystroke timing and accuracy (Zustand for client state).
- Stretch: per-key error rates driving adaptive difficulty or targeted practice text.

## Accounts

Built after the playable slice, superseding the "no accounts in v1" line above. The constraint that
made accounts a non-goal was never the accounts themselves — it was that nothing about them may
become a prerequisite for playing. That constraint still holds and is the design:

- Guest play is unchanged and remains the default. With no Firebase project configured, the account
  UI hides itself entirely and the game is fully playable.
- **A saved run carries no lyrics content.** Track metadata (title, artist, album, lrclibId,
  videoId) plus counts — score, correct/typed characters, lines attempted/completed, typing time.
  Never the lyric lines, never what the player typed, never a per-line breakdown that could
  reconstruct either. This is the offset store's rule applied to a second collection: our
  infrastructure holds identifiers and numbers, never content.
- **All access goes through Express + the Admin SDK.** `firestore.rules` denies every direct client
  read and write. This is what allows submissions to be validated before they land, and keeps
  lifetime stats consistent with the runs behind them.
- Shape validation is not anti-cheat, and is not pretending to be. Scoring happens in the browser
  against lyrics the server never sees, so the server cannot recompute a run. That is an accepted
  consequence of the legal posture. A public leaderboard would need scoring to move somewhere
  verifiable first — worth deciding deliberately rather than discovering later.

Layout: `users/{uid}` (profile + lifetime accumulators), `users/{uid}/runs/{runId}`,
`users/{uid}/bests/{lrclibId}`. Accumulators are stored raw and accuracy/WPM derived on read, so the
headline numbers cannot drift from what they summarize.

### Profile pictures — why there is no storage bucket

Pictures are downscaled to a 256px square **in the browser** and stored inline in the profile
document as a `data:` URI of a few kilobytes. Firebase Storage was the obvious alternative and was
passed over deliberately:

- A bucket is a second service to provision, a second set of rules to write, and a CORS
  configuration to get right — for an asset that is already tiny once downscaled.
- The profile document is read on every page load, so the constraint that matters is "cheap to
  fetch", not Firestore's 1MB ceiling. `MAX_PHOTO_CHARS` is set against the former.
- Canvas re-encoding strips EXIF as a side effect, so location data in a phone photo never leaves
  the user's machine. That is a real privacy win, not a bonus.

**If pictures ever need to be large, this trade flips** and they belong in Storage. The client-side
`fileToAvatarDataUri` is the seam to change.

The server's mime allowlist is security-relevant, not cosmetic: `image/svg+xml` is refused because
an SVG is a document that can carry script, and rendered from a same-origin data URI that script
would run with the page's privileges. The three raster formats cannot execute anything. Validation
lives server-side because a hostile client simply won't run the canvas path.

Accounts are also the natural home for the offset store's per-user attribution when step 8 lands —
`optionalAuth` already tags every request, and consensus weighting by submitter is now possible.

## Setlists — curated difficulty tiers

Added after the build order, and the first feature not driven by the timing problem.

Easy, Medium, Hard, Insane — sharing the pace bands' names — plus Freestyle. Empty by default and
filled by a curator. The estimate grades a song from timings; the curator overrules it, because
required WPM cannot see that a song is all long vowels or dense with proper nouns.

Freestyle is modelled as outside the ladder rather than as a fifth rung, and this is worth keeping:
`PaceBand` is the four measurable tiers, `SetlistTier` is `PaceBand | 'freestyle'`. A measurement
cannot produce Freestyle because Freestyle is defined by having no pace range, and the types make
that a compile error rather than a convention. The move controls and the colour scale follow the
same line — it is off the ladder, not beyond the end of it. An entry stores an LRCLIB id, a video id, metadata
and three aggregate numbers — lyrics are fetched in the browser at play time, exactly as for a
searched track. `toSetlistSubmission` is the enforcement point, the sibling of `toRunSubmission`.

Admin rights come from `ADMIN_EMAILS` / `ADMIN_UIDS`, not a database flag: a stored flag needs a
way to make the first admin, and every version of that is a bootstrapping endpoint to defend
forever or a console edit indistinguishable from an attacker's. Email matching requires the
provider to have verified the address — otherwise the setting means "whoever registers it first".

Two things worth knowing about how 7-9 landed:

- **The offset sign was inverted in the playable slice.** `useGameLoop` computed
  `videoTime + offset` while this document specifies `displayTime = lrcTimestamp + offset`, and the
  on-screen help agreed with this document rather than with the code. Fixed, and pinned by tests in
  `client/src/lib/timing/offset.ts`. It had to be fixed before anything persisted a shared offset:
  a store whose submitters used two conventions has no consensus to find.
- **Confidence is four states, not a threshold.** "Once one user calibrates, everyone after gets it
  right" and "only serve an offset above a confidence threshold" pull against each other. A single
  submission is applied *and* flagged `provisional`, and the next player is asked to confirm rather
  than told it is settled. `contested` is the demotion signal.

## Open questions

- Scoring model: penalize accuracy only, or accuracy plus timing?
- ~~Should nudge adjustments auto-submit, or require explicit confirmation?~~ **Explicit
  confirmation.** Every submission is a button press. A value captured silently at the end of a run
  would carry every abandoned mid-song experiment into the consensus, and an inherited offset
  played back unchanged would vote for itself — which would let one calibration reach `confirmed`
  on its own.
- ~~Minimum submission count before serving a consensus offset?~~ **One, flagged.** Serving nothing
  until three people agree would throw away the property the store exists for. A lone measurement
  is applied and marked `provisional`; three agreeing within 400ms make it `confirmed`.
- ~~What happens when a track has lyrics but no acceptable video match?~~ Answered: the screen says
  so, offers the rejected candidates with their reasons, and keeps the paste form. Nothing about a
  failed match is allowed to be a dead end — a bad heuristic must not make a track unplayable.
- Should nudge adjustments auto-submit, or require explicit confirmation?
- Minimum submission count before serving a consensus offset?
